The forced command `focus-ci`, behind the real sshd with a real CI key, refuses about 30 malformed or hostile requests (shells, scp, sftp, injection, case, spacing, length, an unknown profile) before any docker call. The fake's host starts without the Postgres and collector images, and its `run` and `up --pull never` fail with `No such image` as dev's first deploy did (#28). So the deploy has to pull them by their pinned digests first (#170); a failed pull or an unpinned image stops it at `pull` with nothing run, and rollback and the revert pull an image the host lost. The prod key (#29) gets the same hostile requests plus `candidate` variants. It can't roll back or touch dev, and the dev key can't touch prod. `candidate` reads dev's records without a docker call. It re-points a `:<sha>` that dev moved at prod's digest before `up`, and it records, logs, waits for the lock and stops on a failing step like dev's. Each deploy fails, and the release that ran before starts again by its own digest, under the same lock (a probe checks it's held) and without migrating. Rollback picks the newest known-good release (passed the checks there, not rolled back from), re-tags it from its own digest or pulls it, and never migrates. `rollback <sha>` refuses anything that isn't known-good. A release dev rolled back from isn't promotable to prod until dev runs it again. A rollback whose target fails starts the release it left. The prod rollback key (`rollback-prod`) gets the hostile requests plus `deploy` and `candidate`. It restores only prod's own known-good releases, never touches dev, waits for the lock and gets a clean environment. A client killed during a broken build's start doesn't stop the revert. `rollback … expect <digest>` refuses when another release runs. A `releases.log` line with an empty, odd or repeated key stops deploys, rollbacks and `candidate` with its line number, and a last line without a newline still counts. #117 adds image pruning after every successful deploy or rollback, whichever key: each environment's current, previous and newest known-good releases stay, older ones go and `rollback <sha>` pulls one again, and the pinned images and another repository's image stay. Each `image rm` names only the app's references, is never forced and runs under the lock. A failed deploy prunes nothing, and Docker refusing a removal (an image a container runs), the other environment's malformed log or unreadable references keep the images without failing the deploy. #165 adds the rollback floor: every deploy reads its release's schema (the installed `migration_info.py` on stdin to a one-shot container) before migrating and logs `schema=<head>`, and output it can't read stops it there. A contract deploy writes a floor line first and leaves no rollback target; `rollback` and `rollback <sha>` stop at the floor; dev's floor neither moves prod's nor stops promotion, until prod's own contract deploy sets prod's; pruning then removes releases below both floors. The floor survives a revert and later rollbacks, a contract deploy that fails at start doesn't revert below it, and a failed contract migration still sets it. Needs Docker and network (apt); about 1 min. It runs in a required check, so the network steps retry: the image pull up to 4 times (5, 10, 20 s apart) and apt's downloads 5 times (`Acquire::Retries`, test container only). No systemd in a container, so service management is the one part only tested on the Droplet |

### Which bash the shell harnesses need

The harnesses that run on your machine (`infra/tests/check_config.sh` for `make test-infra`, `infra/tests/prod_stack.sh` for `make test-prod-stack`, `infra/server/tests/run.sh` for `make test-server`) run under the first `bash` on your `PATH`. On macOS that's `/bin/bash` 3.2 unless you installed a newer one, and they work on it: no Homebrew bash needed. Keep them bash-3.2 compatible: no `declare -A`, `mapfile`, `${x,,}`, `${x^^}` or `[[ -v x ]]`. CI runs them under bash 5. To match CI on a Mac, `brew install bash` and make sure Homebrew's `bin` comes before `/bin` on your `PATH`. The scripts `run.sh` starts inside the Ubuntu test container (`in_container.sh`, `focus_ci.sh`, `fake_docker.sh`, `lib.sh`) always run under that container's bash 5, so they can use bash 4+ features.

Bash 3.2 has a trap (#183). When a syntax error or a bad substitution stops a script, for example bash-4-only syntax, bash 3.2 runs the EXIT trap with `$?` still 0. The script then exits 0 and the harness passes halfway through. So every host harness with an EXIT trap sources `infra/tests/exit_guard.sh`: its cleanup calls `exit_guard "$status"`, and the harness's last line is `harness_done`. A run that stops before that line fails with `stopped before its last line, yet with status 0: look for a shell error above`. `scripts/tests/test_harness_exit_status.py` (`make test-scripts`) runs each host harness with a deliberate shell error under every bash it finds (`bash` on `PATH` and `/bin/bash`, so 3.2 on a Mac), with a stub `docker`, and expects a non-zero exit.

## CI

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on every pull request and every push to `main`. A newer push to the same PR cancels the older run. Each job is a required status check on `main` ([infra/github/README.md](../infra/github/README.md)):

| Job (check name) | Runs | Notes |
|---|---|---|
| `Lint and type-check` | `make lint-backend`, `make lint-frontend`, `make lint-scripts`, `make lint-shell`, `make lint-workflows` | |
| `Backend unit tests` | `make test-backend-unit`, then `make test-scripts` and `make test-server` | The script and server bootstrap tests ride in this job so the five required check names stay the same |
| `Backend integration tests` | `make test-backend-integration` against a `postgres:17-alpine` service | Connects as `focus`, a role with `CREATEDB` and `pg_signal_backend` but not superuser (`pg_signal_backend` lets `DROP DATABASE ... WITH (FORCE)` end an autovacuum worker on a test database; #88). **Fails if any test skipped**, since a skip means the database was never reached (`scripts/check_junit.py --no-skips`) |
| `Frontend unit tests` | `make test-frontend` | |
| `End-to-end (Compose stack)` | `make up`, `make check-stack` (health, frontend, sign-up over plain http with the session cookie not `Secure`, telemetry, a save traced end to end with its log line and metric exemplar linked by trace ID, no query strings, paths or cookies in telemetry), then `make test-e2e` | Playwright runs the suites in `frontend/e2e/` against the same stack. `PLAYWRIGHT_BASE_URL` is `http://localhost:8000`; `SIGNUP_MAX_PER_CLIENT` is raised to 1000 so every test can sign up |

Three more jobs aren't required checks (#27, #28, [deployment.md → Images](deployment.md#images-and-production-compose-27)):

| Job | Runs | Notes |
|---|---|---|
| `Image build and production stack smoke` | `make test-infra`, `docker build` of the app image tagged with the commit SHA, then `make test-prod-stack` on it | Every PR and push. On `main` it also saves the tested image as a one-day artifact. Uploads `test-reports-prod-stack` (every container's logs) |
| `Publish image to GHCR` | Loads that artifact and pushes `ghcr.io/ybenzine/ineedtofocus:<sha>` | Only on push to `main`, and only after the five required jobs and the image job passed on that commit (`needs:`). The only job with `packages: write` (`GITHUB_TOKEN`, no stored secret); it checks out no code. Outputs the pushed digest and attests it with `actions/attest-build-provenance` (#128): the only job with `id-token: write` and `attestations: write` |
| `Deploy to dev` | `gh attestation verify` on the digest (#128), then `ssh … "deploy <sha> sha256:<digest>"` through the forced command, reads the record back, then `scripts/smoke_deploy.py https://dev.ineedtofoc.us` | `needs: publish`, environment `dev`. Skips with a notice, green, while the `dev` environment's secrets aren't set ([deployment.md → Deploy to dev](deployment.md#deploy-to-dev-28)). `scripts/tests/test_ci_workflow.py` pins its gate, environment, concurrency group, secrets and provenance check |

The prod deploy is its own workflow, `.github/workflows/deploy-prod.yml` (#29, [deployment.md → Deploy to prod](deployment.md#deploy-to-prod-29)), started by hand only. `scripts/tests/test_ci_workflow.py` pins it to `workflow_dispatch` alone, with the `production` environment, its own concurrency group, secrets only in the deploy job and requests the `prod` profile accepts. It runs the plan step with a fake `gh`, including a tag whose dev deployment never passed its smoke tests, and the resolve step with a fake `ssh`. For build provenance (#128) it pins `publish`'s attestation step and permissions (no other job in any workflow may get `id-token: write` or `attestations: write`), and the verify step's flags, identical in `deploy-dev` and `deploy-prod`. It runs that step with a fake `gh`: an attestation `gh` accepts passes; a missing or mismatched one, or a malformed tag or digest, fails the step, which comes before any `deploy` request. It also checks that the key is deleted before the smoke test runs repository code. For every workflow, it checks that a job reading a secret other than `GITHUB_TOKEN` runs in an environment and that actions are pinned by commit sha.

**Reports.** Each test job uploads a `test-reports-<job>` artifact (14 days): JUnit XML. For end-to-end, the artifact holds `docker compose ps` and the stack's logs, plus `playwright-report/` and `test-results/` once Playwright runs. Each test job also writes a pass/fail/skip table, with skip reasons, to the run's summary page. Coverage isn't collected yet: it needs `pytest-cov` and `@vitest/coverage-v8` in the locked dependencies.

**Actions** are pinned to commit SHAs (with the version in a comment). The workflow token is read-only (`contents: read`), and checkouts don't keep the token. CI uses no stored secrets: the publish job alone gets `packages: write`, `id-token: write` and `attestations: write` on its `GITHUB_TOKEN`.

## Rules

- Every acceptance criterion that describes behavior has at least one test; name tests after the AC where practical (`test_ac13_4_retry_does_not_duplicate`).
- Time-dependent logic uses a fake clock — no real waiting in tests.
- Integration tests use a disposable database; never a shared one.
- Telemetry privacy has its own test (see [observability.md](observability.md)).

## Database for integration tests

`make test-backend` does not start Postgres. Integration tests use the Postgres **server** at `DATABASE_URL` (default: the compose `db` service on localhost, started by `make up`) but never its database: `backend/tests/integration/conftest.py` creates a uniquely named `focus_test_<random>` database per test, runs the Alembic migrations or the test against it, and drops it afterwards (`DROP DATABASE ... WITH (FORCE)`). The dev database is never read or written. The tests skip with a clear reason when the server is unreachable. The role needs the `CREATEDB` privilege (the compose superuser has it). CI provides a Postgres service with a `CREATEDB`, `pg_signal_backend`, non-superuser role and fails the job if any integration test skips (see [CI](#ci)).

Migration tests (`tests/integration/test_migrations.py`) cover upgrade, downgrade to base, repeated upgrade, a single head, drift between the models and the migrations (`compare_metadata` must be empty), and the schema constraints. `tests/unit/test_migration_safety.py` enforces the expand/contract rule (see [architecture.md](architecture.md#data-model)).
