# CLAUDE.md

Claude Code reads this file automatically. The project's agent instructions live in AGENTS.md so every coding agent shares one source:

@AGENTS.md

## Claude Code specifics

- The agent team is defined in `.claude/agents/` (product-manager, backend, frontend, qa, devops, reviewer, oncall). Delegate an issue to the subagent matching its `agent:*` label (`agent:product_manager` → `product-manager`); run the `reviewer` subagent on every PR before merge and the `product-manager` subagent for final acceptance.
- `/work-issue <n>` runs the whole loop for one issue: delegate → PR → review → merge → QA → acceptance. `/work-backlog [milestone]` runs it over the whole backlog, stopping only at human gates.
- Use `gh` for tracker work (comments, PRs, reviews) and `scripts/board-status.sh <n> "<Status>"` to move cards on the board.

## Permissions for unattended runs

`.claude/settings.json` pre-approves routine work (git, `gh`, `make`, Docker Compose, Node/Python toolchains, repo scripts, file edits in the repo and `/tmp`) and denies what sits behind the human gates in `_docs/process.md`: force-push, pushing to `main`, deleting remote branches with `git push` (`--delete`, `-d` or an empty-source `:<branch>` refspec), `gh api` calls on `git/refs/heads/main`, recursive `rm`, deleting repos/issues/releases, `gh api` DELETE calls, setting secrets or variables, changing the repo's visibility, admin merges, the prod deploy workflow (`deploy-prod`, named in #29), and reading `.env` files or the reviewer App's private key (`~/.config/ineedtofocus/`) with Claude's file tools. Remote and destructive commands (`ssh`, `git reset --hard`, removing Docker volumes) and changes to branch protection, rulesets, environments or collaborators ask first. The `rollback` workflow (`rollback.yml`, named in #30) runs without asking so the on-call agent never stalls. Personal overrides go in the git-ignored `.claude/settings.local.json`. The project rules apply once you accept Claude Code's workspace trust prompt for this folder.

These rules match command text, so they prevent mistakes, not determined workarounds: `cat .env` through the shell isn't covered, allowed wrappers (`uv run`, `npx`, `docker exec`, `python`, `node`) run whatever they're given, and `:<branch>` deletes are caught by one rule per first character (`git push * :a*` … `:9*`, since a rule ending in `:*` is read as a literal prefix), so a branch name starting with another character, or a quoted refspec, gets through. `gh pr merge --delete-branch` still tidies up a merged branch. Local `curl` is pre-approved only for explicit ports: `http://localhost:<port>/…` and `http://127.0.0.1:<port>/…` for the backend (8000), Vite dev (5173), Grafana (3000) and OTLP HTTP (4318), plus port 80 and the dev and prod URLs. A rule with `:*` anywhere but the end triggers a startup warning, and its `*` would also match `localhost:x@evil.example`. Put flags before the URL: a `curl` with anything after a `://` URL, such as a second URL, asks first (`curl *://* *`). An extra URL with no scheme, `--url=` or a `-K` config file placed before the allowed URL still gets through. Because the rules match the whole command, words in an inline comment body can trip them too, so tracker bodies are posted from a file (`_docs/process.md` → Posting to the tracker). Run git from the repo root rather than `git -C`, which the rules don't cover. The real backstops are server-side: branch protection on `main` with "include administrators" (once #5 lands) and prod credentials living only in the approval-gated `production` environment.
