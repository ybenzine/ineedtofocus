# CLAUDE.md

Claude Code reads this file automatically. The project's agent instructions live in AGENTS.md so every coding agent shares one source:

@AGENTS.md

## Claude Code specifics

- The agent team is defined in `.claude/agents/` (product-manager, backend, frontend, qa, devops, reviewer, oncall). Delegate an issue to the subagent matching its `agent:*` label (`agent:product_manager` → `product-manager`); run the `reviewer` subagent on every PR before merge and the `product-manager` subagent for final acceptance.
- `/work-issue <n>` runs the whole loop for one issue: delegate → PR → review → merge → QA → acceptance. `/work-backlog [milestone]` runs it over the whole backlog, stopping only at human gates.
- Use `gh` for tracker work (comments, PRs, reviews) and `scripts/board-status.sh <n> "<Status>"` to move cards on the board.
- At most 4 agents run at once per session (#172): the `env` block in `.claude/settings.json` sets `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` and `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` to 4, and a session started before the change must be restarted to pick it up. Details: [_docs/agents.md](_docs/agents.md#orchestration).

## Permissions for unattended runs

`.claude/settings.json` pre-approves routine work (git, `gh`, `make`, Docker Compose, Node/Python toolchains, repo scripts, file edits in the repo and `/tmp`) and denies what sits behind the human gates in `_docs/process.md`: force-push, pushing to `main`, deleting remote branches with `git push` (`--delete`, `-d` or an empty-source `:<branch>` refspec), `gh api` calls on `git/refs/heads/main`, recursive `rm`, deleting repos/issues/releases, `gh api` DELETE calls, setting secrets or variables, changing the repo's visibility, admin merges, starting or approving a prod deploy (#126: `gh workflow run` with `deploy-prod` anywhere in it, as named in #29, or with a numeric workflow ID; `gh api` calls on `pending_deployments` or the GraphQL `approveDeployments` mutation), and reading `.env` files or the reviewer App's private key (`~/.config/ineedtofocus/`) with Claude's file tools. Remote and destructive commands (`ssh`, `git reset --hard`, removing Docker volumes) and changes to branch protection, rulesets, environments or collaborators ask first. The `rollback` workflow (`rollback.yml`, named in #30) runs without asking so the on-call agent never stalls. Running `scripts/reviewer_token.py` directly (or through `uv run` or `python`) asks first, because its stdout is a live GitHub App token and would land in the transcript. Those ask rules match the command text, so running it by absolute path, through `env` or through `bash -c` isn't caught. Like the rest, they prevent mistakes, not determined misuse. `scripts/reviewer-review.sh`, which keeps the token inside its own process, is allowed. That means any agent *can* post an approving review as the reviewer App's bot with `reviewer-review.sh <pr> approve`, and so satisfy the review branch protection requires. Only the reviewer agent's prompt does that; no rule enforces it (#70). The App holds Contents write, needed for its approval to count. A leaked token (valid one hour) could therefore push to any branch other than `main`, approve and merge PRs, and create tags and releases. Three branch protection rules keep it from getting code into `main`: the latest push must be approved by someone other than the pusher (so the bot can't approve its own push), the five CI checks must pass, and administrators are included ([infra/github/README.md](infra/github/README.md#reviewer-github-app-70)). Personal overrides go in the git-ignored `.claude/settings.local.json`. The project rules apply once you accept Claude Code's workspace trust prompt for this folder.

These rules match command text, so they prevent mistakes, not determined workarounds: `cat .env` through the shell isn't covered, allowed wrappers (`uv run`, `npx`, `docker exec`, `python`, `node`) run whatever they're given, and `:<branch>` deletes are caught by one rule per first character (`git push * :a*` … `:9*`, since a rule ending in `:*` is read as a literal prefix), so a branch name starting with another character, or a quoted refspec, gets through. `gh pr merge --delete-branch` still tidies up a merged branch. Local `curl` is pre-approved only for explicit ports: `http://localhost:<port>/…` and `http://127.0.0.1:<port>/…` for the backend (8000), Vite dev (5173), Grafana (3000) and OTLP HTTP (4318), plus port 80 and the dev and prod URLs. A rule with `:*` anywhere but the end triggers a startup warning, and its `*` would also match `localhost:x@evil.example`. Put flags before the URL: a `curl` with anything after a `://` URL, such as a second URL, asks first (`curl *://* *`). An extra URL with no scheme, `--url=` or a `-K` config file placed before the allowed URL still gets through. Because the rules match the whole command, words in an inline comment body can trip them too, so tracker bodies are posted from a file (`_docs/process.md` → Posting to the tracker). Run git from the repo root rather than `git -C`, which the rules don't cover. The real backstops are server-side: branch protection on `main` with "include administrators" (once #5 lands) and prod credentials living only in the approval-gated `production` environment.

The prod deploy rules (#126) are a stopgap with the same limits. Agents' `gh` is logged in as Yacine, who is the `production` environment's required reviewer, so that approval doesn't hold against agents until #127 gives them a credential that can't approve deployments; the rules stay afterwards as a second line. They don't catch a numeric workflow ID placed after a flag (`gh workflow run --ref main <id>`) or quoted (`"<id>"`); a rule like `gh workflow run * 1*` would also match a rollback tag. Nor do they catch a GraphQL query read from a file (`-F query=@file`), or anything run through a wrapper, `bash -c`, `env` or an absolute path to `gh`. Re-runs aren't denied (`gh run rerun`, `gh api …/rerun`): a run ID doesn't say which workflow it belongs to, so a rule would block ordinary CI re-runs too. That's safe while approval is denied: a re-run of `deploy-prod` waits for the `production` approval again. `scripts/tests/test_claude_settings.py` checks the rules are present and that no deny or ask rule matches `gh workflow run rollback.yml …`. Details: [_docs/deployment.md](_docs/deployment.md#deploy-to-prod-29).
